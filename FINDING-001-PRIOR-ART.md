# FINDING-001 — Prior art / novelty check (S-01)

**Date of search:** 2026-08-24  
**Method:** GitHub Issues Search API (unauthenticated) + discussion page fetches + web search for the two Google queries.  
**Finding under test:** Syft writes Debian/Alpine source package as `syft:metadata:source` and PURL `upstream=`; Trivy SBOM ingest reads only `aquasecurity:trivy:SrcName` and silently falls back to the binary name, under-counting distro advisories.

**Gate answer:** Open prior art describes the **same mechanism**. Closest hit is [trivy discussion #7850](https://github.com/aquasecurity/trivy/discussions/7850) (state **open**, answered 2024-11-02 by maintainer DmitriyLewen): Trivy reads `aquasecurity:trivy:SrcName` from CycloneDX properties; Syft stores source in PURL `upstream=`; when the property is absent Trivy uses the binary package name and misses advisories. That is FINDING-001’s mechanism, demonstrated on Alpine rather than Debian and without effect-size tables or the property-copy intervention.

**Publication implication:** Do **not** claim first discovery of the interoperability gap. Claim measured magnitude on Debian images (current syft/trivy), causal intervention, and CRA-facing consequences. Prefer commenting on #7850 (and optionally Syft #1700) over opening a duplicate Trivy issue.

## Anticipated rebuttal (draft before S-05)

**Maintainer may say:** Trivy deliberately ignores `upstream=` because PURL qualifiers are unreliable / not standardized across producers; third-party SBOMs are unsupported by design (docs warn “Passing SBOMs generated by tool other than Trivy may result in inaccurate detection”).

**Answer (strongest card):**

> This is not a request to trust an arbitrary PURL qualifier in isolation. On every Debian component we tested, Syft already populated the source package in **two** places in the same CycloneDX document: (1) property `syft:metadata:source` / `syft:metadata:sourceVersion`, and (2) PURL qualifier `upstream=`. Trivy’s SBOM path reads **neither**. It only looks for its own namespaced property `aquasecurity:trivy:SrcName`. When that property is absent it silently sets `SrcName` to the binary name.
>
> Copying the value Syft already wrote into the property name Trivy already knows how to read restores the vulnerability count to match the direct `trivy image` path (e.g. nginx:1.25 → 137 → 415). No new facts are invented; no unreliable qualifier is being asked to carry the whole story. The gap is that the consumer ignores fields the producer already filled.
>
> We are not asking Trivy to treat every third-party SBOM as equivalent to a Trivy SBOM. We are asking it to read the source-package fields that are already present under the conventions Syft (and the wider PURL `upstream` practice) use, or to fail loudly when `SrcName` cannot be recovered for a distro that indexes by source package. Silent under-count with a soft WARN is the compliance hazard.

## What is *not* prior art (still novel in FINDING-001)

Even though the mechanism is known:

1. **Quantified Debian effect size** across 22 public images (e.g. nginx 67% hidden, node:20-bookworm 92%, golang clean-bill false zero) on current syft 1.51.0 + trivy 0.72.0.
2. **Causal intervention:** copying `syft:metadata:source` into `aquasecurity:trivy:SrcName` restores counts — proves data was present and unread, not missing from the SBOM.
3. **Falsified alternate hypotheses** (DB staleness, VEX cross-suppression, lossy SBOM, OS version drift) with controls.
4. **CRA compliance framing** of silent under-count on a complete SBOM.

Alpine anecdote in #7850 (0 vs 2) does not substitute for that measurement program.
